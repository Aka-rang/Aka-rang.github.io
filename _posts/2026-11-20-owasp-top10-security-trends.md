## 1. 이 주제를 고른 이유

웹사이트에 로그인하면 내 정보와 내가 사용할 수 있는 기능이 보인다. 그런데 주소에 있는 번호 하나를 바꿨다는 이유로 다른 사람의 주문 내역까지 보인다면 어떨까. 로그인은 정상적으로 했어도, 다른 사람의 정보를 볼 권한까지 생기는 것은 아니다.

이번에 정리할 주제는 OWASP Top 10의 **Broken Access Control**, 즉 **접근 제어 실패**다. 나는 취약점을 공부할 때 실제로 어떤 조건에서 문제가 생기는지가 궁금하다. 이 주제도 이름을 외우는 것보다, 서버가 무엇을 확인하지 않아서 문제가 생기는지부터 알아보려고 한다.

## 2. OWASP Top 10은 무엇인가

OWASP Top 10은 웹 애플리케이션에서 중요하게 다뤄야 할 보안 위험을 10개 범주로 정리한 문서다. 개발자와 보안 담당자가 주요 위험을 이해하도록 돕는 자료라고 보면 된다. 이 글은 2026년 11월 20일 확인한 **웹 애플리케이션용 OWASP Top 10:2025**를 기준으로 한다.

여기서 하나의 항목이 하나의 공격 방법만 뜻하는 것은 아니다. 예를 들어 접근 제어 실패에는 다른 사용자의 정보를 조회하는 문제, 권한 없이 관리자 기능을 실행하는 문제 등이 포함된다. 이번 글에서는 이 가운데 사용자 권한을 확인하는 과정에 집중한다.

## 3. 로그인 확인과 권한 확인의 차이

일단 **인증**과 **인가**를 구분해야 한다. 이름이 비슷해서 헷갈릴 수 있지만, 확인하는 내용이 다르다.

| 구분 | 확인하는 내용 | 쇼핑몰 예시 |
|---|---|---|
| 인증 Authentication | 요청한 사용자가 누구인지 | 로그인 정보로 회원 A인지 확인 |
| 인가 Authorization | 그 사용자가 해당 행동을 해도 되는지 | 회원 A가 이 주문을 조회하거나 취소해도 되는지 확인 |

인증을 통과했다고 모든 기능을 사용할 수 있는 것은 아니다. 일반 회원과 관리자는 모두 로그인할 수 있지만, 사용할 수 있는 기능은 다르다. 일반 회원끼리도 각자 자신의 주문 내역을 봐야 한다. OWASP의 인가 가이드도 두 개념을 구분해서 설명한다.

쇼핑몰 직원에게 신분증을 보여줬다고 생각해 보면 이해하기 쉽다. 직원이 내가 누구인지 확인했더라도, 다른 손님의 주문서를 나에게 보여줘도 된다는 뜻은 아니다. 주문서를 꺼내기 전에 그 주문과 나의 관계를 한 번 더 확인해야 한다.

접근 제어에서 내가 기억하려는 기준도 이것이다.

**누가 요청했는지, 어떤 정보를 대상으로 하는지, 그 정보로 무엇을 하려는지까지 함께 봐야 한다.**

## 4. 주문 번호 하나로 이해하는 IDOR

아래는 설명을 위한 가상의 쇼핑몰이다. 이 쇼핑몰의 일반 회원은 본인 주문만 조회할 수 있다고 가정하겠다.

- 회원 A의 주문 번호는 `105`다.
- 회원 B의 주문 번호는 `106`이다.
- A는 자신의 계정으로 로그인한 상태다.

A가 주문 상세 화면을 열면 브라우저는 서버에 다음과 같은 요청을 보낸다.

```http
GET /api/orders/105 HTTP/1.1
```

여기서 `GET`은 정보를 조회한다는 뜻이고, `105`는 조회할 주문을 구분하는 번호다. `/api/orders/105`는 주문 정보를 요청하는 서버의 경로다. 위 코드는 요청의 첫 줄만 나타낸 것이다.

정상적인 서버라면 A가 105번 주문을 볼 수 있는지 확인한 다음 정보를 보내야 한다. 그런데 서버가 로그인 여부만 확인하고 주문 번호에 맞는 정보를 그대로 반환한다고 해보겠다.

A가 요청 속 번호를 `106`으로 바꿨을 때 B의 주문 내역까지 반환된다면 문제가 된다. 서버가 **요청한 주문이 존재하는지는 확인했지만, A에게 그 주문을 보여줘도 되는지는 확인하지 않은 것**이다.

이처럼 데이터나 파일을 가리키는 식별자를 바꿔 권한 밖의 대상에 접근할 수 있는 취약점을 **IDOR(Insecure Direct Object Reference)**라고 한다. 식별자는 주문 번호처럼 숫자일 수도 있고, 파일명이나 문자열일 수도 있다.

여기서 문제가 되는 부분은 번호가 주소에 보인다는 사실 자체가 아니다. 번호를 알아도 권한이 없으면 서버가 접근을 막아야 한다. 사용자가 입력한 값이 숫자인지 검사하는 것만으로도 해결되지 않는다. 106은 정상적인 숫자여도 A가 볼 수 없는 주문일 수 있기 때문이다.

### 번호를 복잡하게 바꾸면 해결될까

주문 번호를 길고 무작위적인 값으로 바꾸면 다른 주문 번호를 추측하기 어려워진다. 하지만 다른 경로로 그 값을 알게 됐을 때도 권한 검사가 필요하다. OWASP도 복잡한 식별자를 추가 방어 수단으로 설명하며, 접근 제어 검사를 계속 적용해야 한다고 명시한다.

내가 보기에는 “다른 사람이 번호를 모를 것이다”라는 예상에 보호를 맡기면 안 된다. 서버는 번호를 알고 요청한 사람에게도 이 데이터를 보여줘도 되는지 판단해야 한다.

## 5. 데이터 접근과 기능 실행을 나눠 보기

접근 제어 실패를 다른 사람의 정보 조회로만 생각하면 놓치는 부분이 있다. **어떤 데이터에 접근하는지**와 **어떤 기능을 실행하는지**를 나눠 보면 이해하기 쉽다.

### 같은 회원인데 다른 사람의 데이터에 접근하는 경우

앞의 주문 예시처럼 일반 회원 A가 일반 회원 B의 비공개 주문에 접근하는 경우다. 관리자 권한을 얻지 않아도 발생할 수 있으며, 이런 형태를 수평적 권한 상승이라고 부른다.

API 보안에서는 특정 데이터에 대한 권한 검사가 빠지거나 제대로 작동하지 않는 문제를 **BOLA(Broken Object Level Authorization)**라고 설명한다. 여기서 객체는 주문 한 건, 문서 한 개처럼 권한을 따져야 하는 대상을 뜻한다. OWASP API Security Top 10:2023은 이를 API1 항목으로 다룬다. IDOR 형태의 취약점도 이런 객체 단위 권한 검사 실패로 이어질 수 있다.

### 일반 회원이 관리자 기능을 실행하는 경우

이번에는 일반 회원에게 회원 전체 목록을 내려받는 기능이 허용되지 않는다고 가정해 보겠다. 화면에서 내려받기 버튼을 숨겼어도, 해당 요청을 서버에 직접 보냈을 때 목록을 반환한다면 기능에 대한 권한 검사가 빠진 것이다.

이처럼 사용할 수 없어야 하는 기능에 접근하는 문제는 **BFLA(Broken Function Level Authorization)**와 연결된다. OWASP API Security Top 10:2023에서는 API5 항목으로 다룬다.

앞의 예시는 사용할 수 있는 주문 조회 기능으로 다른 사람의 주문을 읽은 경우다. 뒤의 예시는 애초에 허용되지 않은 관리자 기능을 사용한 경우다. 둘 다 접근 제어 실패지만, 서버가 확인해야 할 권한의 범위가 다르다.

참고로 API1과 API5는 **별도의 문서인 OWASP API Security Top 10:2023**의 항목이다. 웹 애플리케이션용 Top 10:2025의 번호와 구분해서 읽어야 한다.

## 6. 최근 보안 동향에서 확인할 부분

### 2025판에서도 A01을 유지했다

접근 제어 실패는 OWASP Top 10:2021에 이어 2025판에서도 첫 번째 항목인 A01을 유지했다. OWASP는 여전히 이 문제를 가장 중요한 웹 애플리케이션 보안 위험으로 분류하고 있다.

이 순위를 보고 모든 서비스에서 항상 같은 취약점이 가장 위험하다고 단정할 수는 없다. 다만 내가 여기서 받아들인 점은, 접근 제어가 기본적인 기능처럼 보여도 계속 중요하게 점검해야 할 영역이라는 것이다.

### SSRF가 접근 제어 실패 범주에 통합됐다

2025판의 변화 중 하나는 **SSRF(Server-Side Request Forgery)**가 A01에 통합됐다는 점이다. SSRF는 공격자가 서버의 요청 기능을 악용해, 서버가 의도하지 않은 곳으로 요청을 보내게 하는 문제다.

예를 들어 외부 이미지 주소를 입력하면 서버가 이미지를 가져오는 기능을 생각해 볼 수 있다. 이 기능에서 접근 대상을 제대로 제한하지 않으면, 서버가 외부 사용자에게 허용되지 않은 내부 주소로 요청을 보내는 상황이 생길 수 있다.

이 변화에서 나는 접근 제어를 사람이 사용하는 메뉴에만 한정해서 보면 안 된다고 생각했다. 사용자의 요청을 대신 수행하는 서버에도 허용된 접근 범위가 있어야 한다. IDOR와 SSRF가 같은 공격이라는 뜻은 아니며, 발생 방식과 필요한 방어는 각각 살펴봐야 한다.

## 7. 실제 공개 취약점으로 보는 Next.js 사례

접근 제어 검사가 빠지는 문제는 서비스 개발자가 직접 작성한 코드뿐 아니라 사용하는 프레임워크에서도 발생할 수 있다. 관련 사례로 **2025년 3월 21일 공개된 CVE-2025-29927**이 있다. 공식 권고문은 Next.js의 미들웨어에서 수행하는 인가 검사를 우회할 수 있다고 설명한다.

Next.js는 웹 애플리케이션을 만드는 프레임워크다. 미들웨어는 요청을 본격적으로 처리하기 전에 실행할 로직을 넣는 기능으로 이해하면 된다. 이곳에서 접근 권한을 확인하는 구성이 사용됐다.

이 취약점에서는 내부 처리에 사용되는 요청 헤더를 악용해 미들웨어 실행을 건너뛸 수 있었다. 헤더는 요청에 붙는 부가 정보다. 해당 내부 헤더는 원래 재귀 호출을 방지하고 내부 요청 처리를 조정하는 데 쓰였는데, 외부 요청과의 경계를 제대로 지키지 못하면서 문제가 됐다.

권한을 확인하는 코드가 있어도, 그 코드를 거치지 않고 보호된 기능까지 도달할 수 있다면 접근 제어가 성립하지 않는다. 내가 이 사례에서 중요하게 본 부분이다.

다만 영향 조건은 구분해야 한다. 공식 회고는 취약한 버전을 자체 호스팅하며 `next start` 또는 `output: 'standalone'`을 사용하는 배포 방식을 영향 대상으로 확인했다. Vercel 배포와 정적 내보내기 방식 등은 영향을 받지 않았다고 설명한다. 실제 인가 우회 영향은 미들웨어에서 수행하는 권한 검사와 관련된다.

공식 권고문에는 수정 버전과 임시 완화 방법이 제공됐고, Vercel은 미들웨어만을 경로 보호 수단으로 사용하지 말 것을 권고했다. 이 사례를 통해 나는 권한 검사 코드의 존재뿐 아니라, 중요한 요청이 그 검사를 반드시 거치는 구조인지까지 봐야 한다고 생각했다.

## 8. 그러면 어떻게 막아야 하는가

### 서버에서 대상과 행동까지 확인한다

버튼을 숨기는 것은 화면을 구성하는 방법이다. 실제 접근 허용 여부는 사용자가 임의로 바꿀 수 없는 서버 쪽에서 결정해야 한다. 주문 조회, 수정, 취소처럼 각각의 요청에서 필요한 권한을 확인해야 한다.

앞의 가상 쇼핑몰이라면 다음 항목을 확인할 수 있다.

1. 검증된 로그인 상태를 바탕으로 요청한 사용자를 확인한다.
2. 조회하려는 주문을 확인한다.
3. 그 사용자가 해당 주문을 조회할 수 있는지 확인한다.
4. 권한이 있을 때 주문 정보를 반환한다.

여기서 요청에 적힌 `user_id`를 그대로 믿어서는 안 된다. 사용자가 보낸 번호를 로그인한 사용자라는 증거로 취급하면, 그 번호를 바꿔 다른 사람으로 행동할 수 있기 때문이다. 로그인한 사용자는 서버가 검증한 세션 등의 정보에서 확인해야 한다.

공유 문서처럼 여러 사람이 접근할 수 있는 서비스라면 소유자만 비교해서도 안 된다. 공유 여부, 소속, 역할, 읽기와 수정 권한 등 실제 서비스의 규칙에 맞춰 판단해야 한다.

### 기본적으로 거부하고 필요한 권한만 허용한다

보호할 기능은 허용 조건이 확인됐을 때만 열어주는 방식으로 설계해야 한다. 권한 확인 과정에서 오류가 발생했는데도 요청을 계속 처리하면 안 된다. 사용자에게는 업무에 필요한 범위의 권한만 부여해야 한다. 각각 기본 거부와 최소 권한 원칙에 해당한다.

가상의 쇼핑몰을 예로 들면 배송 담당자에게 배송 정보를 확인하는 권한은 필요할 수 있다. 그렇다고 회원의 권한을 변경하거나 모든 주문을 삭제하는 기능까지 필요해지는 것은 아니다. 역할 이름만 붙이는 데서 끝내지 말고, 실제로 허용할 행동을 정해야 한다.

### 같은 규칙을 모든 접근 경로에 적용한다

주문 조회 화면에서는 권한을 확인하면서 주문서 내려받기에서는 확인하지 않는다면, 다른 경로로 같은 정보가 노출될 수 있다. OWASP는 접근 제어 로직을 공통으로 관리하고 모든 접근 요청에 적용할 것을 제시한다.

이 말은 검사 코드를 한 군데에 만들어 두면 끝난다는 뜻으로 받아들이면 안 된다. 각 API와 데이터 처리 경로에서 필요한 검사가 실제로 적용되는지 확인해야 한다. Next.js 사례를 함께 생각하면 이 차이가 더 분명해진다.

### 허용되면 안 되는 요청도 테스트한다

내 주문이 정상적으로 보이는지만 확인하면, 다른 사람의 주문도 보이는 문제를 놓칠 수 있다. 서로 다른 계정과 각 계정의 데이터를 준비하면 객체별 권한을 비교하기 쉽다.

앞의 가상 쇼핑몰에 적용할 테스트 기준은 다음과 같다.

| 로그인 상태 | 요청 | 기대하는 결과 |
|---|---|---|
| 회원 A | A의 주문 조회 | 허용 |
| 회원 A | B의 주문 조회 | 거부 |
| 회원 B | A의 주문 조회 | 거부 |
| 회원 A | 관리자 전용 회원 목록 내려받기 | 거부 |
| 로그인하지 않음 | A의 비공개 주문 조회 | 거부 |

위 표는 설명용 정책이며, 실제 서비스에서는 역할과 공유 규칙에 맞춰 기대 결과를 정해야 한다.

실제로 확인할 때는 응답 코드와 함께 반환된 내용과 데이터 변경 여부까지 봐야 한다. 거부됐다는 응답이 와도 본문에 다른 사람의 정보가 포함돼 있다면 정보 보호에 실패한 것이다. 수정이나 삭제 요청은 실제 데이터가 바뀌지 않았는지도 함께 봐야 한다. 실습할 때는 직접 만든 로컬 환경이나 허가된 워게임에서 이런 기준을 적용해 볼 수 있다.

## 9. 정리하면서 든 생각

이번 주제를 정리하면서 내가 가장 중요하게 본 것은 **로그인 이후에 서버가 무엇을 확인하는가**다. 앞의 예시에서 A의 계정은 정상이다. 주문 번호 106도 실제로 존재한다. 그래도 A가 그 주문을 봐도 되는지는 따로 판단해야 한다.

Next.js 사례에서는 한 단계 더 볼 수 있었다. 검사를 작성했는지뿐 아니라, 요청이 검사를 건너뛸 수 있는지도 중요했다. 그래서 앞으로 취약점을 공부할 때는 입력값과 응답만 보지 않고, 사용자와 데이터 사이의 권한 관계가 어디에서 확인되는지도 살펴보려고 한다.

특히 워게임이나 개인 실습에서는 “요청이 성공했다”에서 끝내지 않고, **어떤 사용자에게 어떤 행동이 허용됐고, 원래 어떤 규칙으로 막혔어야 하는지**까지 기록하고 싶다. 그렇게 해야 원인과 수정 방향을 같이 설명할 수 있을 것 같다.
